# 按流量 + 时间窗口推送设计方案

> 文档目标：将当前项目从“按带宽 + 时间推送”升级为“按总流量 + 时间窗口推送”，并使生成结果尽可能贴近真实 CDN 业务场景。
>
> 示例口径：以 `2.1PB`、`2026-03-11 00:00:00 ~ 2026-04-10 23:55:00`、`300s` 粒度为例说明。若业务实际年份不同，可替换为对应窗口。

---

## 1. 背景

当前项目的核心生成链路是：

```text
目标带宽 -> 生成带宽曲线 -> 从带宽推导 flux/req/hit 等指标 -> 分配到域名 -> 推送 API
```

当前方案适用于“以平均带宽 / 95 计费带宽为目标”的场景，但不适用于如下需求：

- 已知一个明确的总流量目标，例如 `2.1PB`
- 已知一个明确的时间窗口，例如 `3.11 ~ 4.10`
- 希望生成结果符合真实业务规律：
  - 工作日整体高于周末
  - 白天高于凌晨
  - 周中比周末更活跃
  - 相邻时间点变化平滑，不出现大量锯齿
  - 域名之间有稳定、可解释的业务占比

因此，本次改造的本质不是“把带宽换算成流量”，而是将系统主模型从：

```text
带宽驱动模型
```

升级为：

```text
总流量驱动模型
```

---

## 2. 目标与范围

### 2.1 功能目标

实现一个新的推送模型，满足：

1. 输入总流量目标 + 时间窗口 + 粒度
2. 自动生成每个时间点应推送的流量值
3. 自动推导 API 所需全部指标：
   - `bw`
   - `flux`
   - `bs_bw`
   - `bs_flux`
   - `req_num`
   - `hit_num`
   - `bs_num`
   - `bs_fail_num`
   - `hit_flux`
   - `http_code_*`
   - `bs_http_code_*`
4. 生成结果符合业务常识：
   - 工作日多、周末少
   - 白天高、凌晨低
   - 支持不同业务画像（如 SaaS / 平台 / 游戏）
5. 窗口累计总流量精确命中目标值
6. 支持 dry-run、本地保存、补推、后续扩展到 realtime

### 2.2 第一阶段范围（建议本次实现）

优先完成：

- `simulation`
- `catchup`
- 新配置协议
- 新流量计划生成器
- 新校验器
- 域名维度拆分

### 2.3 第二阶段范围（建议后续实现）

后续补充：

- `realtime` 计划持久化
- dashboard 新图表
- 可配置事件注入 DSL
- 更真实的地区分布

## 3. 当前项目现状分析

### 3.1 当前实现主链路

当前代码核心位于：

- `fake_cdn/core/generator.py`
- `fake_cdn/core/scheduler.py`
- `fake_cdn/core/validator.py`

当前流程大致为：

```text
config.target.bandwidth_gbps
  -> BandwidthCurveGenerator.generate()
  -> MetricsDerivator.derive(bandwidth_gbps)
  -> AnomalyInjector.inject(...)
  -> MultiDimensionDistributor.distribute(...)
  -> Pusher 推送
```

### 3.2 当前实现的限制

#### 1）目标口径仍然是带宽

当前 `config.json` 中主目标为：

```json
"target": {
  "bandwidth_gbps": 20.0
}
```

这意味着：

- 目标是“平均带宽 / 日 95 带宽”
- `flux` 是从带宽二次推导出来的
- 无法保证整段窗口的总流量精确命中一个指定值

#### 2）当前曲线模型是“带宽优先”

`BandwidthCurveGenerator` 当前做法是：

- 先生成日周期、周周期、噪声、突发流量
- 再通过缩放让日 95 接近目标带宽

这套方法不能天然满足：

- 指定窗口总流量 = 2.1PB
- 严格的总量守恒

#### 3）多维分配没有严格守恒

当前 `MultiDimensionDistributor` 使用：

- 平均分域名
- 再乘 `0.9 ~ 1.1` 随机波动
- 不做统一归一化回收

问题：

- 域名间比例不稳定
- 汇总总量可能漂移
- 无法解释业务结构

#### 4）regions 配置目前未真正生效

虽然配置里存在 `dimensions.regions`，但当前生成逻辑实际上固定输出：

- `country = cn`
- `region = mainland_china`

即：

- 配置与实现不一致
- 无法精确表达多地区权重

#### 5）当前校验口径偏向带宽，而不是总流量

`validator.py` 主要验证：

- 平均带宽
- P95 带宽

不能回答关键问题：

- 整个窗口累计流量是否精确等于目标值
- 工作日是否显著高于周末
- 域名占比是否接近配置

## 4. 新方案的总体设计

新方案主链路调整为：

```text
总流量目标(total_flux_bytes)
  -> 构建时间窗口
  -> 生成每日权重(day weights)
  -> 生成日内时间片权重(slot weights)
  -> 叠加业务规律 / 噪声 / 事件
  -> 统一归一化，得到每个时间点的 flux_bytes
  -> 按域名/地区拆分 flux_bytes
  -> 从 flux 推导 bw/req/hit/bs/http_code
  -> 保存 / 推送 / 校验
```

### 4.1 核心设计原则

1. **总流量优先**
   - 内部主目标为 `flux_bytes`
   - 带宽 `bw` 由流量反推得到

2. **总量守恒**
   - 任意随机扰动后，都必须统一归一化
   - 最终严格满足：

```text
Σ slot_flux_bytes = target_total_flux_bytes
```

3. **时间分布真实**
   - 工作日 > 周末
   - 白天 > 凌晨
   - 曲线平滑，避免锯齿

4. **多维结构可解释**
   - 每个域名拥有长期权重
   - 不同域名可配置不同业务画像

5. **结果可复现**
   - 同一配置 + 同一 seed + 同一时间窗口 = 相同结果

## 5. 输入输出口径设计

### 5.1 输入口径

新输入建议为：

- 总流量：例如 `2.1PB`
- 时间窗口：例如 `2026-03-11 00:00:00 ~ 2026-04-10 23:55:00`
- 时间粒度：例如 `300s`
- 时区：例如 `Asia/Shanghai`
- 业务画像：例如 `enterprise_b2b`
- 随机种子：例如 `20260311`

### 5.2 单位约定（必须统一）

建议明确区分：

- `PB = 1000^5 Byte`
- `PiB = 1024^5 Byte`

默认建议：

- `unit = PB`
- `base = 1000`

**禁止默认混用。**

### 5.3 API 输出口径

根据现有 API 文档：

- `flux` 单位：`Byte`
- `bw` 单位：`bit`（当前时间粒度内总 bit）
- 租户界面再按 `bw / interval` 计算 `bps`

因此新模型中：

```text
flux = 当前时间点总流量(Byte)
bw   = flux × 8 (bit)
bps  = bw / interval_seconds
```

## 6. 时间窗口与示例换算

### 6.1 示例窗口

以示例：

- `2026-03-11 00:00:00`
- `2026-04-10 23:55:00`
- 间隔 `300s`

若采用“结束时间包含式”规则，则：

- 共 `31` 天
- 每天 `288` 个点（24 × 60 / 5）
- 总点数：

```text
31 × 288 = 8928
```

### 6.2 2.1PB 的平均量级（十进制）

若以 `2.1PB = 2.1 × 10^15 Byte` 计算：

- 平均每天约：`67.74 TB/天`
- 平均每 5 分钟约：`235.2 GB/5分钟`
- 等效平均带宽约：`6.27 Gbps`

> 注意：这只是平均值，不是最终每个点的推送值。

## 7. 流量计划生成算法设计

### 7.1 整体步骤

```text
1. 解析总流量目标为 bytes
2. 根据时间窗口构建全部时间点
3. 生成 day_weight
4. 生成每个 day 内部的 slot_weight
5. 叠加工作日 / 周末 / 月末 / 噪声 / 事件等因素
6. 对全部 slot 权重归一化
7. 使用整数守恒分配，得到每个时间点的 flux_bytes
```

### 7.2 Day Weight（日权重）

建议默认采用偏 B2B / SaaS 的业务模型。

默认工作日权重建议：

- 周一：`1.08`
- 周二：`1.10`
- 周三：`1.12`
- 周四：`1.08`
- 周五：`1.02`
- 周六：`0.82`
- 周日：`0.78`

再叠加：

- 月初/月末小幅抬升
- 日级平滑噪声（例如 ±3%）
- 可选的活动日加权

公式示意：

```text
day_weight[d] =
    weekday_factor[d]
  × month_edge_factor[d]
  × smooth_day_noise[d]
  × optional_event_factor[d]
```

之后按全部天进行归一化：

```text
day_flux[d] = target_total_flux × day_weight[d] / Σ day_weight
```

### 7.3 Slot Weight（日内时间片权重）

默认 `enterprise_b2b` 画像建议：

- `00:00-06:00`：低谷
- `06:00-08:00`：爬坡
- `08:00-12:00`：上午高峰
- `12:00-14:00`：午间略回落
- `14:00-18:00`：下午高峰
- `18:00-22:00`：缓降
- `22:00-24:00`：回落

可以使用平滑曲线或分段函数实现。

示意：

```text
slot_weight[d, s] =
    profile_shape(hour_of_day)
  × smooth_slot_noise[d, s]
  × optional_slot_event_factor[d, s]
```

同一天内部再做归一化：

```text
slot_flux[d, s] = day_flux[d] × slot_weight[d, s] / Σ slot_weight[d, *]
```

### 7.4 噪声模型

不能使用完全独立的白噪声，否则会产生较强锯齿。

建议：

- 先生成随机序列
- 再进行 EMA 平滑或移动平均

示意：

```text
noise[t] = α × noise[t-1] + (1-α) × random_component
```

这样可以得到：

- 相邻点变化更自然
- 曲线更像真实监控

### 7.5 事件模型

分为两类：

#### A. 流量型事件（影响流量计划）

例如：

- 月底导出
- 活动拉升
- 版本发布
- 下载高峰

这类事件应作用在 `slot_weight` 上，然后再统一归一化，保证窗口总流量不变。

#### B. 指标型异常（不改变总流量）

例如：

- 5xx 增加
- 命中率下降
- 回源失败率上升
- 4xx 激增

这类事件应在指标推导后执行，不允许直接破坏 `flux` 总量。

## 8. 整数守恒分配策略

由于 API 字段均为整数，因此必须实现一个通用“整数守恒分配器”。

适用场景：

- 将总流量分配到每一天
- 将一天流量分配到 288 个时间片
- 将单时间片流量分配到多个域名
- 将请求数分配到各 HTTP 状态码

建议算法：**最大余数法（Largest Remainder）**。

### 8.1 输入

- `total_int`
- `weights[]`

### 8.2 输出要求

- `result[]` 为整数
- `sum(result) == total_int`
- 分配结果尽可能接近权重比例

这是保证：

```text
整窗精确命中 2.1PB
```

的关键基础设施。

## 9. 多维度拆分设计

### 9.1 设计原则

不再使用“全局指标先生成，再随机拆到域名”的方式。

建议改为：

```text
slot_total_flux
  -> 先按 domain / region 拆出子流量
  -> 每个叶子节点独立 derive_from_flux
  -> 生成最终单条 API 日志
```

### 9.2 域名配置建议

当前域名建议从 `list[str]` 改为 `list[object]`：

```json
"domains": [
  {
    "name": "benchling.com",
    "weight": 0.06,
    "profile": "enterprise_b2b"
  },
  {
    "name": "megacrit.com",
    "weight": 0.04,
    "profile": "game_content"
  }
]
```

### 9.3 域名拆分策略

对每个时间点：

```text
domain_flux[i] = slot_total_flux × domain_weight[i] × domain_time_factor[i]
```

然后统一归一化并做整数分配，确保：

```text
Σ domain_flux[i] = slot_total_flux
```

### 9.4 地区拆分策略

第一阶段建议：

- 若 API 或业务暂不要求多地区，先固定一个地区
- 或者真实使用 `regions.weight` 做二次分配

第二阶段可扩展为：

```text
slot_total_flux
  -> domain split
  -> region split
  -> leaf metrics derivation
```

### 9.5 业务画像差异

建议提供三类默认画像：

- `enterprise_b2b`
- `balanced_platform`
- `game_content`

不同画像可体现在：

- 日内曲线形状不同
- 周末折扣不同
- 平均对象大小不同
- 命中率分布不同
- 回源比例不同

## 10. 指标推导设计（从 flux 推导）

### 10.1 新的推导顺序

从：

```text
bandwidth -> flux -> other metrics
```

调整为：

```text
flux -> bw -> req_num -> hit/bs -> http_code
```

### 10.2 推导规则

假设输入：

- `flux_bytes`
- `interval_seconds`
- `profile`
- `timestamp_ms`

则：

#### 1）带宽字段

```text
bw = flux_bytes × 8
```

#### 2）命中率与回源流量

```text
cache_hit_rate ∈ [0.85, 0.95]（或按 profile 调整）
bs_flux = flux × (1 - cache_hit_rate)
hit_flux = flux - bs_flux
```

#### 3）请求数

```text
avg_object_size = 根据 profile 采样
req_num = flux / avg_object_size
```

#### 4）命中请求数 / 回源请求数

```text
hit_num + bs_num = req_num
```

#### 5）回源失败数

```text
bs_fail_num = bs_num × origin_fail_rate
```

#### 6）状态码分布

客户端侧：

- 2xx
- 3xx
- 4xx
- 5xx

回源侧：

- bs_http_code_2xx
- bs_http_code_3xx
- bs_http_code_4xx
- bs_http_code_5xx

所有状态码分配必须采用整数守恒分配，保证：

```text
2xx + 3xx + 4xx + 5xx = req_num
bs_2xx + bs_3xx + bs_4xx + bs_5xx = bs_num
```

### 10.3 一致性要求

任意一条日志都必须满足：

```text
bw = flux × 8
hit_flux + bs_flux = flux
hit_num + bs_num = req_num
http_code_2xx + http_code_3xx + http_code_4xx + http_code_5xx = req_num
bs_http_code_2xx + bs_http_code_3xx + bs_http_code_4xx + bs_http_code_5xx = bs_num
```

## 11. 模块改造方案（按当前项目结构）

### 11.1 `fake_cdn/core/generator.py`

#### 当前问题

- 强耦合在“带宽曲线生成”
- 分配逻辑未严格守恒
- 推导逻辑以带宽为中心

#### 改造目标

新增 / 重构如下组件：

1. `TrafficTargetParser`
2. `FluxCurveGenerator`
3. `TimeWindowBuilder`
4. `MetricsDerivator.derive_from_flux()`
5. `MultiDimensionDistributor`（支持精确拆分）
6. `CDNLogGenerator.generate_window_logs()`

#### 建议职责

- `TrafficTargetParser`
  - 解析 `PB/PiB`
  - 转换 bytes
- `TimeWindowBuilder`
  - 生成完整时间点序列
- `FluxCurveGenerator`
  - 生成每个时间点的 `flux_bytes`
- `MetricsDerivator`
  - 从 `flux_bytes` 推导全部指标
- `MultiDimensionDistributor`
  - 先分流量，再生成叶子维度日志
- `CDNLogGenerator`
  - 总控流程

---

### 11.2 `fake_cdn/core/scheduler.py`

#### 第一阶段

重点改造 `CatchupScheduler`，支持任意时间窗口补推。

建议：

- 不再依赖 `duration_days`
- 改为使用：
  - `start_datetime`
  - `end_datetime`
  - `interval_seconds`

#### 第二阶段

改造 `RealtimeScheduler` 为“计划驱动”：

- 首次生成 `traffic_plan.json`
- state 中记录 `plan_id`、`current_index`
- 重启后继续使用已有计划，不重新随机生成

---

### 11.3 `fake_cdn/core/validator.py`

#### 当前问题

- 更关注平均带宽 / P95
- 对 `bw` 的解释偏向 bps，而文档中 `bw` 实际是时间段内总 bit

#### 改造目标

新增 `FluxWindowValidator`：

- 校验总流量是否命中
- 校验工作日与周末差异
- 校验峰谷比
- 校验域名占比
- 校验字段守恒关系
- 输出等效平均带宽、P95 带宽（作为参考值）

### 11.4 `fake_cdn/cli.py`

#### 改造目标

- 增加新配置协议校验

- 输出总流量、等效带宽、日均统计

---

### 11.5 `fake_cdn/core/pusher.py`

#### 改造建议

- 保持推送协议不变
- 补充导出 `flux_curve.csv`

  - `target_total_flux_bytes`

### 11.6 `fake_cdn/core/storage.py`

## 15. 验收标准

### 15.1 硬性指标

1. 时间点数正确

以示例窗口：

```text
2026-03-11 00:00:00 ~ 2026-04-10 23:55:00
interval = 300s
points = 8928
```

2. 总流量精确命中

```text
Σ slot_flux_bytes = target_total_flux_bytes
```

允许误差目标：

- 理想：`0`
- 最多：`<= 0.1%`

3. 关键字段守恒

必须满足：

```text
bw = flux × 8
hit_flux + bs_flux = flux
hit_num + bs_num = req_num
2xx + 3xx + 4xx + 5xx = req_num
```

### 15.2 真实性指标

1. 工作日平均日流量 > 周末平均日流量
2. 峰谷比合理（建议 `1.8 ~ 3.0`）
3. 相邻时间点波动平滑
4. 域名长期占比接近配置

### 15.3 可重复性指标

同一：

- 配置
- 时间窗口
- random seed

重复生成结果必须一致。

## 17. 风险与注意事项

### 17.1 单位歧义风险

`PB` 与 `PiB` 若不明确，会导致目标误差明显。

必须在配置中显式声明：

- `unit`
- `base`

### 17.2 时间口径风险

必须明确：

- 使用时区感知 datetime
- `end_datetime` 为包含式
- 开始/结束时间必须与粒度对齐

### 17.3 补推量级风险

当前项目约有 `34` 个域名。

以示例窗口估算：

```text
8928 × 34 = 303,552 条日志
```

若未来再叠加多地区，推送量会显著上涨。

建议第一阶段先控制维度复杂度。

### 17.4 realtime 漂移风险

如果 `realtime` 每次启动都重新生成计划，会导致：

- 已推部分与未推部分不在同一条曲线上
- 窗口总流量漂移
- 无法复现

因此第二阶段必须增加计划持久化。

## 18. 结论

本次改造建议明确以“总流量驱动模型”为核心：

```text
总流量目标
  -> 时间分布计划
  -> 维度拆分
  -> 指标推导
  -> 推送
  -> 流量校验
```

与当前方案相比，新的方案可以同时解决：

1. **总流量精确命中**
2. **工作日 / 周末分布更真实**
3. **域名结构更合理、可解释**
4. **可复现、可补推、可扩展到 realtime**

建议实施优先级：

1. 先改配置与流量计划生成器
2. 再改指标推导与维度拆分
3. 再接入 `simulation/catchup`
4. 最后扩展 `realtime` 与 dashboard
