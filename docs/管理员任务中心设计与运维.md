# 管理员任务中心设计与运维

## 1. 目标与边界

配置中心只负责配置生命周期，不在保存、发布或回滚时隐式生成数据。实际执行统一
从管理员任务中心发起，任务引用创建时的不可变配置版本，避免发布新版本后改变已经
排队的任务。

普通账号仍只能访问绑定 `tenant_id` 的数据页面；任务中心、配置管理和审计接口在
路由、布局和每个 Dash 回调中都再次检查管理员会话。

## 2. 执行链路

```text
管理员页面 /admin/jobs
        │  JobService 校验 + 幂等键
        ▼
SQLite generation_jobs(status=queued)
        │  Worker 原子 claim
        ▼
run-job 子进程
        │  resolve_version(config_version_id)
        ▼
simulation / catchup / realtime
        │  心跳、日志、统计
        ▼
succeeded / failed / cancelled / interrupted
```

### 2.1 任务模式

- `simulation`：按配置完整生成窗口，可强制 Dry-Run。
- `catchup`：必须填写开始和结束时间，范围不能超出发布版本，且按
  `interval_seconds` 对齐。
- `realtime`：当前时间必须位于发布版本窗口；单次执行使用 `once`，持续执行必须
  设置结束时间。

真实推送任务同时满足配置 `dry_run=false`、API 环境变量存在和管理员二次确认才会
进入队列。环境变量只在执行进程注入，不写入配置版本或任务参数。

## 3. 状态机与恢复

```text
queued → running → succeeded
   │         │
   │         ├── failed
   │         ├── cancel_requested → cancelled
   │         └── Worker 重启 → interrupted
   └── cancelled
```

同一租户在 `queued`、`running`、`cancel_requested` 状态最多存在一个任务；参数和
版本组成的 `dedupe_key` 也有唯一约束。Worker 启动时会把上次遗留的活动任务标记为
`interrupted`，并记录审计事件。停止 Worker 时先发送 `SIGTERM`，超时后强制结束，
未完成任务记为 `interrupted`。

## 4. 数据与审计

`generation_jobs` 记录：

- `config_version_id`、校验和和租户，保证版本可追溯。
- `parameters_json`、`dedupe_key`、进程 PID、Worker ID、心跳和取消时间。
- 每个任务独立 `output_dir` 和 `job.log`，生成日志写入中央 `FAKE_CDN_DB_PATH`。

任务创建、领取、取消、终态、重试和中断均写入 `config_audit`。配置数据库升级时会
自动补齐新字段；如果旧库有多个活动任务，会保留最新的一条，其余标记为
`interrupted` 后再创建活动任务唯一索引。

## 5. 运维操作

### 本地

```bash
python -m fake_cdn tenant-migrate --config ./config.json --config-db output/config.db
python -m fake_cdn dashboard --config ./config.json --config-db output/config.db --port 8050
python -m fake_cdn worker --config-db output/config.db
```

### 生产

```bash
./scripts/deploy.sh full
./scripts/deploy.sh status
./scripts/deploy.sh stop
```

systemd 使用 `fake-cdn-dashboard.service`、`fake-cdn-worker.service` 和
`fake-cdn.target`。Dashboard 使用 Gunicorn，Worker 使用独立进程；两者共享 SQLite
WAL 数据库和 `.env`，但不会共享 Python 进程状态。

### 排障顺序

1. `systemctl status fake-cdn-dashboard fake-cdn-worker` 检查服务状态。
2. `journalctl -u fake-cdn-worker -n 100` 查看 Worker 领取和子进程退出原因。
3. 在 `/admin/jobs` 查看任务的 `error_text`、心跳、日志尾部和输出目录。
4. 若 Worker 重启，先确认任务已变为 `interrupted`，再由管理员点击重试。
5. 真实推送失败时先检查 `.env`，不要直接修改已发布版本；修正后重新创建或重试任务。

## 6. 发布与回滚

代码发布前运行完整测试和 `git diff --check`，然后按运维技能要求先确认生产部署。
部署时先停止旧 Worker，再更新依赖和代码，最后启动 target 并检查 Dashboard、Worker
和任务队列。配置回滚使用配置中心的历史版本回滚按钮，不直接编辑数据库或覆盖
`config.json`。
